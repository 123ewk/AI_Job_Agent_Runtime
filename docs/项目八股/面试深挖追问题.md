## ① 项目业务逻辑类

### Q1. 「你把整个平台跑通的全流程给我走一遍——从用户打开招聘网站,到一个岗位真正被沟通,数据是怎么一步步流动的?」

【参考答案】
用户在自己的 Chrome 里打开 Boss 直聘列表页(这是关键前提:页面是**用户真人在看的**,不是我们去爬)。我注入一段脚本去读页面里 Vue 实例挂的数据 `$data.jobList`,把这页的岗位拿出来——注意这**一个 zhipin 请求都不发**,所以 Boss 的反爬机制不会触发。拿到的岗位先进 `job_fit` 做确定性预筛(薪资、地点、外包关键词,不达标直接弃),然后幂等落库,状态是 discovered。

落库之后会触发任务入队,按优先级进 Redis Streams。消费端把任务拿出来,交给 WorkflowEngine 启动一个 LangGraph 图实例:`receive_task` 先把任务元数据和历史会话装进状态,`classify` 归一任务类型,`planner` 调 LLM 决定这一步干什么(是去调某个技能、还是需要人工审批、还是结束),`skill_router` 把"目标"映射成具体 skill,`tool_executor` 在浏览器锁里调 MCP 执行。如果执行失败,走 `error_recovery` 分类处理。中间如果涉及敏感操作,走到 `approval` 节点会 interrupt 挂起等人工审批,`resume` 注入决策后再继续。最后 `sync` 落库,图进终态。

【面试口述小提示】
- 这是"主链路题",先讲**大方向**(采集→落库→入队→图执行→审批→落库),再往细节补。别一上来就钻 interrupt 底层。
- 一句话点出"页面是用户真人打开的、零新增请求",这是你和普通爬虫方案的本质区别,很加分。

### Q2. 「人工审批在你系统里是个什么角色?什么时候会触发?审批挂起期间系统在干嘛?一直不批怎么办?」

【参考答案】
审批是**安全闸**。不是所有操作都要批,只有 planner 判定这是 doc14 里那几类敏感操作(比如发消息、投递这类对外动作)时,`approval` 节点才触发。实现上是在这个节点调 LangGraph 的 `interrupt()`,图就暂停在这一点,把"审批请求"暴露给外部;审批人(前端 WebSocket 推送过去)approve/deny 后,用 `Command(resume=决策)` 把决策注入回来,图继续往下跑。

挂起期间系统**没有其他任务能插进来**——因为执行锁在挂起时**不释放**,锁还握在手里,新任务进来只能等。这一点是有意设计的:严格单任务,V1 简化成"暂停不释放锁"。一直不批的话,审批有超时机制(20 秒),超时会走一个兜底决策,不会永远卡着。

【面试口述小提示】
- 重点讲"interrupt 挂起 + 锁不释放 + 超时兜底"三件套,说明你想过"挂起期间并发怎么办"。
- 如果被追问"超时后默认是批还是拒",如实说:非法/超时按 deny 处理(代码里非法决策按 deny),理由是自己拿不准就不该让机器自作主张。

### Q3. 「你的岗位落库为什么要做幂等?同一个岗位被抓到两次,底层会发生什么?」

【参考答案】
因为 Boss 列表页你往下翻就会反复看到同一批岗位,而且队列 at-least-once 语义下消息可能重复投递,如果每次抓到都新建一条记录,DB 里会堆满重复岗位,列表页、统计就全乱了。所以落库用 `(platform, external_id)` 做唯一键去重——Boss 每个岗位有唯一 ID,同一岗位再来,直接返回已有记录,不新建。

配合在消费端还有一个幂等检查:任务入队后真正执行前,先查这个任务是不是已经终态了,是的话直接 ACK 跳过,不执行——这样即使消息被重投,任务已经跑完也不会跑第二遍。

【面试口述小提示】
- 把"幂等"拆成**两个层面**答:数据落库幂等(唯一键)+ 任务消费幂等(终态检查)。说明你想过重复来自哪里。
- 面试官可能会问"为什么不用 409 报错",答:重复是正常业务预期,不是错误,静默返回已有记录更合理。

### Q4. 「你说从 Boss 页面提取岗位,具体怎么做到的?为什么会失败?失败了怎么办?」

【参考答案】
主路径:向页面注入脚本,在 MAIN world(和页面脚本同一个世界)直接读 Vue 实例内部挂的数据 `$data.jobList`——岗位的薪资、公司、标题都是明文,直接能拿到。这条路**不发任何网络请求**,所以 Boss 的"检测到自动化就拒绝"那套机制抓不到我们。

兜底路径:如果注入失败(比如页面结构变了、Vue 数据没挂上),降级用获取页面文本内容(DOM)的方式解析;但 Boss 对正文做了**反爬字体**,直接读文本薪资会乱码,所以这条路径的岗位薪资会置空并打 warning,不硬编。

整个提取是一个**垂直 skill**(boss-extract-jobs),职责是"提取→预筛→幂等落库"三件事,返回统一的结果结构,失败会标记 error_kind 让上层图决定走不走恢复分支。

## ② 技术选型 & 取舍类

### Q5. 「你任务队列用的 Redis Streams,为什么不用 RabbitMQ?要是流量变大你怎么扩?」

【参考答案】
三个理由:第一,我们本来就部署了 Redis(会话、缓存、后面还要用),Streams 是 Redis 内置的,**复用已有的组件**,不用为队列再引一套 RabbitMQ 这种有状态 broker,运维面和故障面都少一块。第二,需求恰好是 P0-P3 四级优先级 + at-least-once + 死信 + 崩溃恢复,Streams 的**消费组**原生覆盖这些,不需要额外插件。第三,对比 Kafka,我们是单应用、量级很小的任务队列,Kafka 那套高吞吐 + 分区管理 + KRaft 运维是杀鸡用牛刀。

如果流量变大:当前是单 Worker + 单消费组。可以先加消费者实例,但要注意——消费组内每条消息只给组里一个消费者,扩容时如果单流成为瓶颈,Streams 可以按优先级分流(我们已经是四条流),进一步可以按任务维度分片;真到了需要大吞吐、多租户、长期消息保留的场景,再评估迁 Kafka,接口层已经抽象在 QueueClient 后面,替换成本可控。

【面试口述小提示】
- 这个题面试官大概率会问,因为**你原简历写的是 RabbitMQ 而实际是 Redis Streams**——千万别被绕进去,大方承认"我们用的是 Redis Streams",然后把上面的取舍讲清楚。
- "接口抽象、可替换"是很好的收尾点,体现架构意识。

### Q6. 「为什么用 LangGraph?这活儿自己写个状态机不也能干吗?」

【参考答案】
能,但 LangGraph 给的几样东西自己写很容易出错、而且难测:一是**显式状态图**——8 个节点 + 条件边,图和状态是"一等公民",编译期能校验结构,比手写 while 循环 + if-else 分支可读、可测得多;二是 **interrupt / checkpoint**——人工审批要"图跑到一半暂停、之后从断点续跑",这个语义 LangGraph 内置,手写要处理一大堆暂停/恢复/状态序列化;三是 **RetryPolicy** 节点级重试,planner 调 LLM 失败可以在编译期声明"这个节点瞬时失败自动重试",手写得自己在每个节点包 try/retry。

更重要的是我们做了**依赖倒置**:graph 不反向依赖 runtime,定义 `GraphRuntime` 协议,生产注入真实引擎、测试注入 FakeRuntime——所以图的核心逻辑能用纯单元测试覆盖(176 个 pytest 里 graph 就占 24 个)。对比 AutoGen(偏多智能体对话)、CrewAI(偏多 Agent 分工),我们这是单 Agent 工具调用链 + 人工审批,LangGraph 的"可控状态图"最贴合。

代价是踩了不少坑:LangGraph 版本 API 不稳定,1.2.9 实测 interrupt/Command/RetryPolicy 的位置、参数名都变过,节点函数注解还要求运行时能解析,否则编译时 NameError。

【面试口述小提示】
- 答到"依赖倒置 + 能单测"是亮点,面试官会觉得你不是"会用库"而是"会设计"。
- 最后带一句"版本 API 坑"很真实,但别展开太多,提一下就行。

### Q8. 「岗位匹配你搞了个 LLM 80% + 关键词 20%,为什么不干脆纯 LLM 或纯规则?」

【参考答案】

## ③ 底层实现原理类(重点)

### Q9. 「LangGraph 的 interrupt() 到底是怎么做到『图跑到一半暂停、下次接着跑』的?状态存哪?」

【参考答案】
你可以把它想成**调试器在断点处暂停**。图是一个状态机,每跑完一个节点,当前"每个通道的值"(就是 AgentState 那一整包)会被存进一个 checkpoint。`interrupt()` 是个特殊节点,它调用的时候不是普通 return,而是往图里写一个"打断标记",把暂停点暴露出来,然后图的执行栈就停在这里——但状态没丢,冻结在当前 checkpoint。

要恢复,外部用 `Command(resume=值)` 再调图,图从那个 checkpoint 把状态捞回来、恢复执行栈,`interrupt()` 这一行就"返回"你注入的值,图继续跑后面的节点。审批就是这个:approval 节点 interrupt 暴露"要不要发这条消息",前端批了 approve,`resume('approve')` 回来,节点拿到决策继续。

状态存哪取决于 checkpoint saver:测试我们用内存的 InMemorySaver,生产计划用 AsyncPostgresSaver(把 checkpoint 序列化进 Postgres),这样进程重启也能从磁盘恢复挂起任务——这是整个"挂起恢复"能成立的地基。

【面试口述小提示】
- 核心是**"checkpoint + 从断点续跑"**这两个词,再加调试器类比,面试官就懂你理解了这个机制。
- 别去扯 LangGraph 内部图的递归调用/递归深度那些实现细节,面试官通常要的是"能讲清楚暂停和恢复的状态去哪了"。

### Q10. 「你搞了个两级锁:执行锁 + 浏览器锁。为什么必须是这个顺序?asyncio.Lock 有什么坑?」

【参考答案】
先说什么锁:**执行锁**保证同一时刻只有一个 Agent 任务在跑(单 Worker 下防任务互相踩状态);**浏览器锁**保证所有对 Chrome 的工具调用串行——Chrome 是单实例共享资源,一次只能干一件事。

为什么顺序固定"先执行锁、后浏览器锁"?为了**防死锁**。设想两个协程:A 拿了执行锁、在等浏览器锁;B 拿了浏览器锁、在等执行锁——两个互相等对方释放,就死锁了。固定成唯一的拿锁路径后,不可能出现交叉等待,死锁从结构上被排除。获取还带超时(执行锁 600s、浏览器锁 120s),超时抛 LockTimeoutError 上抛让上层决策,而不是傻等。

asyncio.Lock 的坑:第一它**不绑定持有者**,谁都能 release,这既是坑也是特性——我们有意利用它:run() 挂起(interrupt 暂停)时执行锁不释放,由 resume() 的终态路径负责释放,保证挂起期间没有别的任务插进来;第二它**非重入**,同一个协程持锁时再 acquire 自己会死锁,所以所有获取都走 wait_for 超时兜底,并且代码里明确禁止嵌套获取同类锁。

【面试口述小提示】
- "固定锁序防死锁"是核心考点,类比"红绿灯都按同一个方向转就不会撞车"。
- 能讲出"锁序 + 超时 + 不绑定持有者"三层,面试官会认为你真的处理过并发。

### Q11. 「Redis Streams 消费组是怎么保证 at-least-once 的?消息卡住了、消费者挂了,怎么恢复?死信怎么进?」

【参考答案】
Stream 是个像日志一样的追加结构,生产者 `XADD` 往 stream 尾部写消息。消费组把消费者组织起来,**组内一条消息只发给一个消费者**,这是负载均衡。消费者 `XREADGROUP` 读走消息后必须 `XACK` 确认;没确认的消息会留在 pending 列表(PEL)里——这就是 at-least-once 的来源:只有确认了才从组里移除,没确认的随时可能被重投。

三种异常场景:
1. **消费者挂了**:消息停在 PEL,`XPENDING` 能查出"谁消费了但超时(30s)没 ACK",`XCLAIM` 把它转移给别的消费者重跑,这就是崩溃恢复。
2. **执行失败**:重试计数 +1,没到上限就重新入队,到了上限 `XADD` 进独立的死信 stream,不再重试,保留现场供排查和告警。
3. **消息重复投递**:消费前先查任务是否已终态,是就直接 ACK 跳过——配合任务状态机,保证重投不重跑。

【面试口述小提示】
- 只要讲出 **XADD → XREADGROUP → XACK** 这条主链 + **PEL/XCLAIM** 恢复 + **死信**三条,这道题就稳了。
- 被追问"为什么至少要一次而不是恰好一次",答:恰好一次需要幂等消费端配合,我们靠"终态检查"在外面补了幂等,等价达到了效果,这是分布式系统常见取舍。

### Q12. 「听说你修过一个『DB 惰性引擎自死锁』,整个服务都挂死了?根因是什么?怎么定位的?」

【参考答案】
背景:数据库引擎是**惰性初始化**的(第一次用才创建,因为模块级创建会绑定错误的事件循环)。两个惰性单例各自用一个非重入的 `threading.Lock` 保护"只初始化一次"。

根因是**锁嵌套**:`get_session_factory()` 拿着自己的父锁,然后去调 `get_engine()`,而 `get_engine()` 内部又要 acquire 同一个非重入锁——**同一个线程自己锁自己**,直接死锁。因为非重入锁不能重复进入。第一次请求触发冷启动时踩中,那个请求线程永远卡住;FastAPI 异步应用里 DB 初始化没完成,后续所有依赖 DB 的请求全堵住,**表现为整个服务挂死**。

排查过程:先看到的是"第一个触 DB 的请求卡死、后续全挂",一开始以为是连接池满了或者事件循环被阻塞;逐步定位到是同步锁死锁——用堆栈/traceback 看到两个单例的锁互相在等同一个非重入锁。修复:在**父锁外**先把 engine 拿好(get_engine 自带 double-checked locking),父锁内不再调用子单例的加锁入口,从根本上消除锁嵌套。

沉淀出的原则:**惰性单例的父锁里,不能调子单例的加锁入口**。这个 RCA 写进了 docs/issues/,后来代码评审都拿这条当红线检查。

【面试口述小提示】
- 这是你**最有分量**的一段,面试官最爱听。重点讲三点:现象≠根因(先误判是连接池)、非重入锁自死锁的本质、修复=消除锁嵌套。
- 别背代码,讲**你当时怎么一步步排出来的**——排查过程的逻辑比结论更值钱。

## 附:压力追问快问快答(项目一)

> 这几个是"如果流量变大 / 出故障"的快速压力题,每道 20-30 秒口述即可。

### P1. 「如果同时有 100 个用户用,你的单 Worker 架构会怎样?」
【参考答案】执行锁是进程内的 asyncio.Lock,单 Worker 下天然只能串行跑一个任务,100 个用户的任务会排队,吞吐上不去。但浏览器锁是"Chrome 单实例"决定的——每个用户其实需要自己的浏览器会话,所以真正扩展是**多 Worker + 每用户独立浏览器**:执行锁要换成 Redis 分布式锁(TTL + 续约,LockManager 注释里已经预留了这个替换点),浏览器锁按 user 维度隔离。我会先讲清"锁的 V1 是单 Worker 语义,接口已经为分布式锁预留"。

### P2. 「挂起中的任务存在内存里,进程一重启就丢了,怎么办?」
【参考答案】这是已知风险。方案是 checkpoint 落库(AsyncPostgresSaver)+ 队列里挂起的消息重投(stalled 恢复),这两块在接线清单里。当前诚实答案:挂起态和锁在内存,重启会丢,恢复能力依赖 checkpoint_store 落地。

### P3. 「LLM 调用超时/挂了,你的图怎么处理?」
【参考答案】planner 节点声明了 RetryPolicy,瞬时 LLM 失败节点级自动重试;重试仍失败抛错走图异常分支。注意坑:max_attempts 是含首次的(=2 只重试 1 次),语义和直觉不一样,我们按 doc 对齐并标了风险。

### P4. 「页面结构变了,提取不到岗位,链路会怎样?」
【参考答案】skill 失败会标记 error_kind(DOM_CHANGE 这类),图进 error_recovery:可恢复类型(页面变了)走浏览器恢复后重试,重试超上限转 failed;规则违反这种不可重试的直接 failed 不再重试——分类恢复是有意区分"值得重试"和"重试也没用"。

## 一屏速览(面试前扫一眼)

- 链路:**入库** = 文档解析 → 清洗(表格/页眉页脚/代码块) → 按标题层级递归分块(相邻块重叠) → BGE 向量化 → FAISS 索引;
  **问答** = query 向量化 →「FAISS 稠密 + BM25 稀疏」多路召回 → RRF 融合 → Cross-Encoder 重排 → 相关性阈值过滤 → 构造上下文 → LLM 生成 + 引用定位
- 分块:按标题层级递归切分 + 相邻块重叠(替代固定长度切分,解决"打断语义单元→召回缺陷")
- 混合检索:稠密(BGE,512 维)+ 稀疏(BM25,中文先 jieba 分词),RRF 融合(score = Σ 1/(k+rank),k=60)
- 重排:bge-reranker(cross-encoder)对融合后 Top-N 打分排序,阈值过滤低置信片段
- 反幻觉:仅依据给定片段作答的提示词约束 + 来源不足拒答 + 引用编号硬校验 + Top-K 截断
- 评估:小规模人工标注问答集,以"召回命中(recall@k)"为基线,做分块/K 值/阈值调优

# ① 项目业务逻辑类

### Q1. 「你从把一个文档传进系统,到用户拿到带引用的回答,整个过程给我完整走一遍。数据是怎么一步步走的?」

【参考答案】
分两段讲:入库和问答。

**入库(一次性)**:文档进来先做格式识别——PDF 用 pdfplumber/PyMuPDF 按页提文字,Word 用 python-docx,Markdown 直接按结构读。拿到原文先清洗:表格转成结构化文本、去掉页眉页脚、代码块单独标记,防止脏文本污染后面的切分。清洗完按标题层级递归分块,相邻块之间留重叠;每一块调 BGE 模型向量化,得到 512 维向量,连同"文档名、章节标题、页码"这些元数据一起写进 FAISS 索引。索引建完,这条文档就能被检索了。

**问答(每次查询)**:用户的问题先同样过 BGE 变向量;同时用 jieba 分词后过 BM25。两路分别召回(设计上比如各 Top-50):FAISS 按向量相似度取最近邻,BM25 按词项命中取前 50。两路排名用 RRF 融合成一个综合排名,取融合后 Top-20 送进 Cross-Encoder 重排——重排器把 (query, 每个片段) 拼在一起打分,得到更准的相关性分,排序后按阈值砍掉低相关的片段,最后留下高置信的 Top-5 左右。这些片段按相关度排好拼进提示词的"资料区",告诉模型"只准用这些资料回答、标注来源、资料里没有就说没有",模型生成回答,引用自动带上片段编号和来源定位。

【面试口述小提示】
- 主链路题,先讲大框架"入库 vs 问答"两段,再补每段子步骤,别一开始就钻 BM25 公式。
- 把"**多路召回 → 融合 → 重排 → 过滤 → 生成**"这个顺序背熟,这是 RAG 工程的标准骨架,面试官会顺着这个骨架往下追。
- 里面 Top-50 / Top-20 / Top-5 是**设计上的经验值**,答的时候说"设计上"/"待评估集定",别说得像实测过。

---

### Q2. 「用户问『公司公积金比例是多少』,系统是怎么决定把哪些片段送进大模型的?Top-K 是怎么定的?」

【参考答案】
分三层:召回、压缩、过滤。

第一层召回:query 向量化后,FAISS 返回相似度最高的 N 个块,BM25 返回词项命中最多的 N 个块。这里**召回量故意放大**(各 50),因为召回阶段**宁可多捞、不能漏**——漏掉相关片段,后面再准也白搭。

第二层融合压缩:50+50 不能全送模型,先 RRF 把两路排名合并成一份 Top-20。

第三层重排+过滤:Top-20 进 cross-encoder,它比向量相似度理解得更细(能同时看 query 和片段词的交互),打完分按阈值砍——分数低于阈值的片段即使被召回也直接丢掉,不进上下文。这一步是**防幻觉的关键**:宁可少给,不把噪声喂给模型。最后留 Top-5 左右拼进上下文。

Top-K 怎么定:**评估驱动,不拍脑袋**。我建了一个小的人工标注问答集,标好"每道题的正确答案在哪个块",跑不同 K 值看"召回命中的比例",选平衡点。K 太大上下文脏、模型容易被带偏、token 也贵;K 太小容易把相关块挤掉。⚠️ 具体数字要等我跑完评估集,现在是经验值,口述别报死数。

【面试口述小提示】
- 核心是讲出"**召回大、重排压缩、阈值过滤**"三层,以及"K 是评估出来的不是拍出来的"。
- ⚠️ 诚实点:如果评估集还没跑,就说"评估集在搭,当前用经验值,计划用 recall@k 来定",不要编一个 K 值。

### Q3. 「你简历写『回答附带引用定位』,这个引用是怎么保证真实的?模型自己会编引用,你怎么防?」

【参考答案】
引用不是靠模型自觉,是靠**结构性硬校验**。提示词里我会给每个片段编号,告诉模型"答案里只能引用给出的片段编号,不能发明编号,资料里没有的内容就说不知道"。这样引用在**形式上可校验**:模型输出的每个编号,后端都去查"这个编号对应的片段是不是真的在送进去的资料集里",不在就直接拦掉或标出来,不会原样展示。

另一个层面是**溯源闭环**:送进去的每个片段本身带元数据(文档名、章节、页码),所以即使模型引用了,我拿到编号也能一路回查到"这句话出自哪个文档哪一页"。面试官如果追问"模型只给你个编号你能信吗",答案是:信不信不由模型说了算,由"编号在不在资料集里"这个硬校验说了算。

【面试口述小提示】
- 关键词是"**硬校验**"——引用真实性靠后端校验兜底,不靠提示词自觉,这体现你考虑过幻觉的工程面。
- 别吹"100% 防幻觉",可以说"降低到能校验、能拦截的程度,残余风险是模型编的内容恰好编得合理"。

# ② 技术选型 & 取舍类

### Q4. 「为什么用 FAISS?不用 pgvector、Milvus 或者 Elasticsearch?」

【参考答案】
我的场景是**单机、万级块、自建知识库**,FAISS 是库不是服务,`pip install faiss-cpu` 直接内存索引,零部署成本,数据和业务代码在同一个进程里,最简单。对比:
- **pgvector**:要有个 Postgres,而且业务库和向量库分开,涉及"双写一致"问题——文档更新了,关系表改了,向量索引也得跟着改,两边同步是个坑;
- **Milvus**:这是给百万级、多租户、分布式场景设计的独立向量数据库,为一个个人知识库引一套服务端中间件(部署、监控、运维)是杀鸡用牛刀;
- **Elasticsearch**:自带 BM25 和 kNN 检索,能一站式做混合检索,但它也是独立服务,我们这规模用不上它的分词和分布式能力。

结论:FAISS 在"数据量小、要快、要省事"时最合适。什么时候换?数据到几十万块以上、或要多人并发强隔离、或要持久化和故障恢复时,再评估 Milvus/ES——但 repository 层(索引操作)封装成了接口,换后端上层不用动。

【面试口述小提示】
- 取舍核心论点是"**规模决定选型**",不是"FAISS 就是最好"。把"双写一致""运维成本"讲出来很加分。
- 被追问"FAISS 重启就没了怎么办",提前想好:分块和元数据落库了,索引可重建(或索引文件落盘加载),不是丢数据,是重建成本的问题。

### Q5. 「你为什么搞混合检索(稠密+稀疏)?纯向量检索哪里不够?为什么融合选 RRF 不选加权平均?」

【参考答案】
纯向量检索的缺陷是**语义匹配但词不达意**——BGE 理解"意思像不像",但对**精确词项**不敏感:岗位 JD 里的编号、"公积金 12%"这种数字、代码里的函数名、专有名词,语义向量可能把它们当无关,导致召回漏掉。BM25 恰好相反,它只看**词项命中**:文档里出现过这些词就高分,不关心意思。两者互补:向量管语义,BM25 管精确词。

融合为什么用 RRF 不用加权平均?加权平均先要解决一个问题:**两路分数不在一个量纲**。FAISS 给相似度(0~1),BM25 给 IDF×词频那种几十分、几百分的原始分,直接乘权重相加,量纲大的一路会主导,还得手动归一化、调两个权重,很脆。RRF 干脆不看分数只看**排名**:score = Σ 1/(k+rank),两路排好名次按名次合并,天然无尺度、不用调权重,k 取 60 是业界经验值。它不追求最优,追求**鲁棒**——两路里只要有一路把正确片段排进靠前名次,RRF 就能把它抬上来。

【面试口述小提示】
- 这道题考的是"**懂不懂两路检索的互补本质 + 量纲问题**"。把"语义 vs 精确词项""分数不在一个量纲"讲清楚就赢了。
- 被追问"加权平均什么时候更合适",答:只有一路、或分数可归一化且你有把握调对权重时,加权也许更精细;多路、分数异构时 RRF 更稳。这是经典取舍。

### Q6. 「为什么要有重排这一层?cross-encoder 为什么不在召回阶段直接用?阈值怎么定的?」

【参考答案】
召回阶段要快、要能捞回候选,**召回模型必须是"廉价相似度"**——bi-encoder(BGE)把 query 和文档各自编码成向量、算个点积,一次能对几万条打分,毫秒级。但局限是 **query 和文档没交互**:编码时各算各的,只能靠"向量方向像不像"判断相关,细粒度的词级、句级匹配看不见。

cross-encoder 把 (query, 文档) **拼成一句一起喂进模型**,内部有完整自注意力,query 的每个词都能"看"文档的每个词,理解更细更准——代价是每对都要过一遍模型,慢几十倍。所以不可能对全库跑,只能**对召回后的 Top-N 重排**:先便宜地捞 50,再精确地排 20,这是"**召回要广、重排要准**"的分层设计。

阈值怎么定:没有公式,在**评估集上试出来**——我会标注"哪些片段对这道题相关",看不同阈值下"该留的留下多少、该砍的漏掉多少",选平衡点。阈值太高把相关片段也砍了(漏检),太低噪声又混进来(误检),这是个权衡。

【面试口述小提示】
- 把"**bi-encoder 无交互、cross-encoder 有交互**"这个底层区别讲出来,面试官就知道你不是只会调 API。
- 阈值强调"评估驱动 + 漏检/误检权衡",别报一个拍脑袋的阈值数字。

### Q7. 「为什么用 bge 这个 embedding?为什么选 small?你对比过别的吗?」

【参考答案】
选型标准三条:**语言适配、尺寸、检索友好**。我的知识库以中文为主,必须选中文本地化好的模型。bge 是中文第一梯队的开源 embedding,而且官方明确写了"**检索场景要在 query 前加 instruction 前缀**"——这是个很实的坑:裸用 bge 检索效果会打折,加了前缀才对齐它的训练方式。这是我实测对比出来的,不是看来的。

选 small 不选 base/large:embedding 是**每块文本都要算一次**,数据量上来后嵌入成本是主要开销;small 维度低(512 维)、速度快,对万级块完全够用;base 效果略好,但为那点提升付出成倍的时间和存储不划算。对比过:和 openai text-embedding 比,bge 免费可本地跑、隐私好;和通用多语言模型比,纯中文场景 bge 更轻更准;以后要做多语言再评估换 bge-m3。

【面试口述小提示】
- 能讲出"instruction 前缀"这个坑是强信号——说明你真跑过、对比过。
- 别堆模型名,讲清"**按语言/尺寸/检索友好三条标准选**"这个思考框架比罗列更重要。

# ③ 底层实现原理类(重点)

### Q8. 「FAISS 检索底层大概怎么跑?Flat 和 IVF、HNSW 什么区别?数据怎么走、瓶颈在哪?」

【参考答案】
FAISS 本质是"给向量建索引,让找最近邻变快"。最基本的 **Flat 索引就是暴力比对**:query 向量和库里每个向量算相似度,排序取 Top-N,精确但 O(N) 逐条比,数据一多就慢。

**IVF** 的思路是**先粗分桶**:用 k-means 把全库向量聚成 nlist 个簇,每簇有个质心;查询时先算 query 离哪些质心近,只搜最近的 nprobe 个簇,不在这些簇里的根本不用比——牺牲一点精确度(边界处的向量可能被漏)换大提速。nprobe 越大越准越慢,这是第一个要调的旋钮。

**HNSW** 建一个**分层图**:每层是一些点连成的图,上层稀疏、下层密集;查询从最顶层一个点开始,沿"离 query 越来越近"的方向往下跳,逐层细化。优势是召回率高、查询快,缺点是建索引慢、内存高、不方便删除。个人项目万级数据用 Flat 都行,再大用 IVF,追求高召回用 HNSW。

数据怎么走:query → 向量化 → 按索引结构定位候选 → 逐个算相似度 → 取 Top-N 返回候选 id → 后端拿 id 查块内容和元数据 → 送下游重排。瓶颈通常在**向量都在内存里**(几十万条×512 维×4 字节很吃内存)和 **nprobe 等参数没调好导致召回率下降**,不是 CPU。

【面试口述小提示】
- 能讲出"Flat 暴力 / IVF 粗分桶 / HNSW 分层图"三个结构和"nprobe 是精确度旋钮"就稳了。
- 被追问"余弦还是欧氏",答:向量归一化后内积=余弦,**相似度度量要和 embedding 模型训练时一致**(bge 配 cosine),这是常见坑。

### Q9. 「BM25 到底怎么打分?为什么中文要先分词?稀疏向量和稠密向量本质区别是什么?」

【参考答案】
BM25 是"关键词命中"打分:衡量**一个词在文档里值多少分**。两个核心因子:IDF(**词越稀有越值钱**,"公积金"比"的"值钱得多)和**词频饱和**(词出现越多分越高,但到一定程度饱和,防长文档堆词作弊),还有文档长度归一化(同一个词,短文档里出现比长文档里出现更说明问题)。它不需要机器学习,公式算出来,可解释。

中文必须分词,因为**中文没有空格**,"知识库"不能按"字"匹配(BM25 按 token 匹配,"知""识""库"拆开就配不上)。所以先 jieba 切词成"知识/库/检索/增强",再去算词项命中。英文有天然空格,分词这步轻很多。

稀疏 vs 稠密:BM25 给每个文档生成一个**高维但大部分是 0** 的向量(词典几万词,只有命中的词位非零)——叫稀疏向量,只能表达"有没有这个词",表达不了意思。稠密向量(embedding)把整个语义**压缩进 512 个浮点数**,每个维度都有值,词间语义关系已隐式编码——所以 512 维反而能表达"意思",只是对精确词项不敏感。这也是为什么两个要合起来用。

【面试口述小提示】
- 讲清"IDF + 词频饱和 + 长度归一化"三个因子 + "中文为什么必须分词",底层感就出来了。
- "**稀疏=有没有这个词、稠密=语义压缩**"这个对比是灵魂,务必用自己的话讲顺。

### Q10. 「cross-encoder 和 bi-encoder 底层到底差在哪?为什么 cross 更准却更慢?」

【参考答案】
架构完全不同。**bi-encoder 是两个独立编码器**:query 单独编码成向量,文档单独编码成向量,相关性 = 两个向量的点积/余弦。编码时 query 和文档**互不接触**,信息在"变成向量"那一刻就各自固定了,交互被推迟到"算夹角"这一步——所以快(文档向量都预存好了),但"能不能配对上"取决于向量方向像不像。

**cross-encoder** 把 (query, 文档) **用分隔符拼成一段文本**,送进一个模型跑完整自注意力:每一层里 query 的每个 token 都会 attend(看)文档的每个 token,词与词直接交互。相关性强弱在深层交互里"算出来",所以对"字面不像但语义相关""需要推理对应关系"的情况判断更准。代价是**每对都要完整 forward 一次**,而 bi-encoder 的文档向量是预计算的,查询时只算 query 一次 + 一堆点积。这就是为什么 cross 慢几十倍、只能用来重排 Top-N。

打个比方:bi-encoder 像"看简历照片挑人"(先各自拍照再比照片像不像);cross-encoder 像"两个人坐下来聊一句"(信息直接交锋),当然更准也更费时。

【面试口述小提示】
- 用"**交互发生在哪一步**"来回答:bi 的交互在向量点积,没有词级交互;cross 的交互在自注意力,词级全接触。
- 先说原理再说类比("照片 vs 对话"),别只给类比。

### Q11. 「固定长度分块为什么会打断语义?你最后用的递归分块到底怎么切?overlap 有什么用?」

【参考答案】
固定长度就是"每 512 字一刀切",问题是**刀会切在不该切的地方**。一段话、一个概念、一段代码可能被拦腰切断:比如"公积金比例是 12%"被切成了"公积金比例是"和"12%",后半句孤零零的。切完每个块都是"语义残片":要么块不完整(答案被切成两半谁也答不全),要么语义太碎(embedding 一个残片,向量方向都是偏的)——这就是"召回缺陷"的根因。

递归分块按**文档结构优先级**层层切:先按最高级标题切出章节,章节太大按段落切,段落太大按句子切,句子还大才按固定长度兜底。它保证**大多数块落在语义完整的位置**(章节、段落、句子),而不是硬生生 512 字一刀。LangChain 的 RecursiveCharacterTextSplitter 就是这个思路,只是分隔符优先级要按中文习惯调(换行 > 句号 > 逗号)。

overlap 是**相邻块之间重复留一小段**(如 50 字),解决"边界信息丢失":一句话正好跨在两个块边界时,这句在两个块里各露半截,检索任何一个都可能因残缺而不相关;留了重叠,边界处的完整句子在下一块里是完整的,不会被边缘化。

【面试口述小提示】
- 核心讲"**语义残片 → 召回缺陷**"的因果链——这是你简历上"定位固定长度切分打断语义单元的召回缺陷"这句话背后的原理,必须能展开。
- overlap 讲"防边界信息丢失"就够,别扯太多。

### Q12. 「你说检索噪声会导致幻觉,底层机制是什么?你的提示词和阈值过滤真的能压住吗?」

【参考答案】
先讲机制。大模型生成时是"顺着上下文内容续写",它**分不清哪段资料相关、哪段是噪声**——你给它 5 个片段,里面混 1 个不相关的(比如另一个文档里恰好提到同一个词),模型可能**把这个噪声片段当依据**,编出一段看着合理、其实张冠李戴的答案。这就是"检索噪声 → 幻觉"的链路:召回漏了相关的、混了不相关的,送到生成阶段,模型被带偏。

两道防线:
1. **过滤**:重排后按相关性阈值砍掉低置信片段,让噪声尽量不进上下文——从源头减少"模型能拿到的错误依据"。
2. **提示词约束**:告诉模型"只能依据给定资料回答,资料没有的必须说明'资料未提及',不得自行编造",限制模型"脑补"的自由度。

但**必须诚实**:这两道防线只能**显著降低,不能 100% 消除**。因为(1)阈值本身是权衡,砍太狠会把相关片段误杀;(2)提示词是软约束,资料确实不完整时模型仍可能"合理填补"。真正确保不瞎说,还得靠**引用硬校验**(模型引用的编号必须是送进去的片段)+ 上线前人工抽检。面试主动承认这个局限,比吹"解决了幻觉"可信得多。

【面试口述小提示】
- 这道题最考真诚:承认"只能降不能消",给出"过滤 + 提示词 + 引用校验"三层,面试官会认为你真思考过幻觉。
- 被追问"实测幻觉率降了多少",⚠️ 如实说:指标没跑,用定性结论("过滤后明显少了无依据编造"),不要报虚假百分比。

## 附:压力追问快问快答(项目二)

> 这几个是"如果流量变大 / 出故障"的快速压力题,每道 20-30 秒口述即可。

### P1. 「知识库里根本没有这个问题的答案,你的系统会怎么表现?」
【参考答案】设计上是"拒答优先":检索出的片段相关度都不够高(阈值过滤后所剩无几),就走到低置信分支,模型明确回答"资料中未找到相关内容",而不是硬编。⚠️ 这个拒答分支要真实跑过才算数——当前是设计,别当已实现。

### P2. 「同时有 100 个用户问,系统哪里先扛不住?你怎么改?」
【参考答案】瓶颈依次:①LLM 生成(单次几百毫秒到几秒,串行会排队)→ 加并发但要注意 API 限流;②embedding(每次查询一次,可缓存 query 向量);③重排(cross-encoder 每对一次,GPU 上才快)。改造方向:查询结果按 query 哈希缓存、批量 embedding、重排换 GPU 推理、检索/生成拆服务横向扩。个人项目先讲清"缓存 + 并发 + 分批"就够。

### P3. 「LLM 接口超时或者挂了,你的链路会怎样?」
【参考答案】设计上有重试(瞬时错误重试 N 次,指数退避)和降级(LLM 挂了返回"服务暂不可用",或降级只返回检索到的相关片段让用户自己看)。⚠️ 当前是设计,面试如实说实现进度。

### P4. 「你的文档更新了或者删除了,FAISS 索引怎么同步?」
【参考答案】这是 FAISS 的经典痛点:内存索引,不支持方便的单条删除。设计思路是**索引可重建**:分块和元数据落库,文档变更时对该文档的分块重新向量化,整体重建索引(小数据量重建很快)或"标记失效 + 定期重建"。增量更新是后续优化点,当前先保证"重建路径正确"。

# 项目接口整体测试报告

## 1.测试概况

- **项目来源**：解析提供的项目源码 `AI_Job_Agent_Runtime/backend`（FastAPI 应用，入口 `app/main.py`，v1 路由聚合在 `app/api/v1/router.py`）
- **接口总数量**：**58 个 HTTP 接口** + 2 个 WebSocket 接口（`/ws/tasks/{task_id}`、`/ws/user`，附注说明）
- **请求头约定**：JSON 请求体接口一律要求 `Content-Type: application/json`；**全项目无鉴权头**——`get_current_user_id()` 固定返回 `user_id=1`（源码标注 `TODO: V2+ 接入 JWT`，V1 单用户模式设计）
- **测试覆盖场景**：正向正常、分页/数值/长度边界、空值、缺失必填、非法类型、特殊字符与注入样例、业务异常（404/403/409/去重/并发限制）、依赖不可用（DB/Redis/LLM 未配置）
- **模拟执行方式**：基于源码 + Pydantic/FastAPI 框架语义**静态推演模拟**（未连接真实服务与数据库），"模拟实际响应"为契约级预期推演
- **测试用例数量**：共 **254 条**模拟用例
- **测试人员**：AI 模拟

**模拟响应的统一格式**（与源码 `app/core/exceptions.py` + `main.py` 全局异常处理器一致）：
- 参数校验失败：`422`，`{"detail":[{type, loc, msg}]}`
- 资源不存在：`404`，`{"error":"not_found","message":"..."}`
- 参数非法：`400`，`{"error":"bad_request","message":"..."}`
- 归属校验失败：`403`，`{"error":"forbidden","message":"..."}`
- 业务冲突：`409`，`{"error":"conflict","message":"..."}`
- 未捕获异常：`500`，`{"error":"internal_error","message":"服务器内部错误"}`

## 4.全局缺陷汇总

| 缺陷ID | 所属接口 | 严重等级 | 缺陷现象 | 复现入参 | 修复建议 |
|---|---|---|---|---|---|
| D01 | POST `/conversations/{id}/sync` | 一般 | `sync_boss_messages` 为占位 stub（`service/conversation.py:291`），永远返回 0 条、仅更新 `last_synced_at`；接口提示"同步完成，新增 0 条消息"误导调用方 | 任意会话调 sync | 接入 Boss Chat Skill / Chrome 拉取并去重落库；或移除该端点避免假成功 |
| D02 | POST `/memory/extract` | 一般 | `extract_and_save` 为占位 stub（`service/memory.py:459`），永远"新增 0 条记忆"，无实际 LLM 提取 | `?conversation_id=3` | 实现 LLM 记忆提取，或标注"未实现"并返回明确错误 |
| D03 | POST `/memory`、`/memory/search` | 一般 | embedding 为占位零向量（`service/memory.py:495`），>0.95 去重与语义排序基于零向量余弦，检索结果无意义、去重判据失真 | 写入/检索任意记忆 | 接入真实 embedding 模型（bge-small-zh 或 OpenAI/火山 API）并 L2 归一化 |
| D04 | GET `/jobs/hr`（路由冲突） | 轻微 | `/jobs/{job_id}` 定义在 `/jobs/hr/list`、`/jobs/hr` 之前，GET `/jobs/hr` 会命中 `{job_id}` 且 int 解析失败返回 422，而非 405/404，语义混乱 | `GET /api/v1/jobs/hr` | 调整路由注册顺序：静态路径优先于 `{job_id}` |
| D05 | POST `/tasks/{id}/approvals/approve` | 轻微 | 请求体 `approved` 必填但后端逻辑完全未使用（只用 `approval_id`/`user_note`），传 `approved=false` 同样获批，前后端契约有歧义 | `{"approval_id":1,"approved":false}` | 要么使用 `approved` 值，要么从请求体移除该字段 |
| D06 | POST `/conversations/{id}/messages` | 轻微 | `MessageCreate.conversation_id` 请求体必填，但路由强制覆盖为 path 值；前端必须多传一个与服务端一致的字段，且传错值会被静默覆盖 | 不传 body conversation_id → 422 | 将请求体字段设为可选或移除，统一以 path 为准 |
| D07 | GET `/conversations/{id}/messages` | 轻微 | `limit` 参数无上限校验（默认 100），可传超大值导致全表查询/内存压力 | `?limit=999999999` | 加 `le` 上限（如 500） |
| D08 | GET `/memory/conversation/{id}`、`/memory/job/{id}` | 轻微 | `limit` 无上限校验（默认 50） | `?limit=999999` | 加 `le` 上限 |
| D09 | GET `/browser/token`、POST `/settings/active` | 待确认 | 无用户鉴权（仅本机 IP/域名+CORS 限制）；浏览器桥令牌明文返回，局域网/公网部署时可能被滥用 | 任意来源（突破 CORS 后）请求 | 加鉴权头或令牌校验；明确部署边界 |
| D10 | 全部接口（`get_current_user_id`） | 待确认 | 用户 ID 固定返回 1，全接口无真实鉴权（`api/deps.py` TODO JWT） | 任意请求 | V1 单用户已知设计；V2 接入 JWT 前不暴露公网 |
| D11 | GET `/tasks/queue/stats` | 轻微 | `max_concurrent` 硬编码为 3，未读取用户配置 | 用户并发配置改为 5 | 从 SettingsService 读取 |
| D12 | POST `/memory/context/for-task/{id}`、GET `/tasks/{id}/approvals/pending` | 轻微 | 任务查询未按 user_id 过滤（`task_repo.get(task_id)`），多用户下存在越权读取风险 | 他用户任务 ID | 查询带 `user_id` 条件 |
| D13 | GET `/health/db`、`/health/ready` | 待确认 | DB 异常时仍返回 HTTP 200（body 内 status=error），若监控仅以状态码判定故障将漏检 | 停掉 DB 后探活 | 探针可按依赖重要度返回 503，或明确监控策略 |
| D14 | PUT `/settings/job-rule` | 轻微 | 无 `min_salary ≤ max_salary` 交叉校验，可落自相矛盾规则 | `{"min_salary":30,"max_salary":10}` | 增加交叉校验（422） |
| D15 | PUT `/settings/reply-style` | 轻微 | `tone/formality/length_preference` 描述为三选一但无枚举校验，任意字符串可入库 | `{"tone":"aggressive"}` | 加 Literal/枚举校验 |
| D16 | POST `/jobs`、`/jobs/hr` | 轻微 | 幂等去重命中时仍返回 201 Created（返回库中已有记录），语义上应 200 | 重复 POST 同 external_id | 去重命中返回 200；或保持 201 但前端按 idempotent 处理并明确文档 |
| D17 | POST `/jobs`（external_id）、POST `/conversations/{id}/messages`（content）、POST `/memory`（content） | 轻微 | 必填字符串均无 `min_length`，空串/纯空白可入库，破坏数据质量与去重锚点 | `{"external_id":""}`、`content:""` | 对业务锚点与内容字段加 `min_length=1`（可 strip 后校验） |
| D18 | PUT `/settings/batch` | 待确认 | 未知 `category` 的落库行为未确认，可能写入任意 key | `{"category":"unknown",...}` | 服务端对分类白名单校验，非法分类返回 400 |

## 5.整体测试结论

**统计**：58 个 HTTP 接口 + 2 个 WebSocket；共模拟执行 **254 条用例**。按用例判定：**通过 196 条、失败 39 条、待确认 19 条**（占比如下）。接口层面：**51/58 通过**，**7 个接口存在确认性缺陷**（API-39 sync、API-56 extract、API-15/17/22/37/38/49/52/53 等关联缺陷），另有 6 处【待确认】依赖源码不足（D18、任务重试/取消状态机细节、简历默认互斥、会话去重、关闭幂等性）。

**总体通过率（按用例）**：约 **77.2%**；若剔除 19 条待确认用例，明确用例通过率约 **83.4%**。

**主要风险与遗留问题**：
1. **三个"假成功"接口**（D01/D02/D03）最值得关注：sync 与 memory extract 均返回 `ok` 和"新增 0 条"，调用方（Agent 同步节点、任务完成回调）无法感知功能未实现，属于**静默失败**，比直接报错更危险。
2. **鉴权整体缺失**（D10/D09）：V1 单用户是刻意设计（源码多处 TODO 注明），但 `/browser/token` 返回令牌、`/settings/active` 收明文 api_key，一旦脱离本机部署即构成数据/令牌泄露面，上线前必须加固。
3. **参数校验盲区**：多个必填字符串无 `min_length`（D17）、若干 `limit` 无上限（D07/D08）、回复风格无枚举校验（D15）、薪资区间无交叉校验（D14），会在数据层累积脏数据。
4. **路由顺序隐患**（D04）：`/jobs/hr` 被 `{job_id}` 抢占返回 422，同类模式（`/conversations/unreplied/check`、`/tasks/queue/stats`）因路径段数不同暂未触发，但属结构风险，扩展新路由时需注意静态路径优先。
5. **契约冗余/不一致**（D05/D06/D16）：请求体存在被忽略的必填字段（`approved`、`conversation_id`），幂等创建返回码语义不一致，前端易误解。

**优化建议（按优先级）**：
1. 立即：给 stub 接口（sync/extract）加"未实现"明确报错或真实实现，消除静默成功。
2. 上线前：补齐鉴权（JWT）与 `/browser/token` 的令牌校验；修复路由顺序；实现真实 embedding。
3. 低成本高收益：补 `min_length`、`limit` 上限、枚举/交叉校验，共 6 处 Schema 级修改即可覆盖 D07/D08/D14/D15/D17。
4. 明确化：DB 探针返回码策略、`approved` 字段去留、幂等创建返回码，统一为前端文档契约。

> 报告完毕。所有结论均基于源码静态分析，模拟响应为契约级推演；标注【待确认】与【源码信息不足】的条目建议补充真实接口文档（或运行环境实际调用）后复核。
